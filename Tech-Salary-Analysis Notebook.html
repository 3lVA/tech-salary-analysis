Dropping Rows Where Pay Period is not Yearly¶

The dataset contains 5 pay periods types: hourly, weekly, bi-weekly, monthly, & yearly. To make salary comparisons accurate and meaningful, I restricted the analysis to YEARLY salaries. This decision is based on the following reasons:

  1. Consistent salary scale: Yearly salaries are already on a common scale. In contrast, hourly, weekly, & monthly salaries cannot be directly compared without converting assumptions.
  2. Avoiding unrealistic assumptions: Converting hourly or weekly salaries to yearly would require assuming fixed working hours per week and fixed weeks per year. These assumptions may not match the actual job requirements and would introduce artificial bias into the analysis.
  3. Cleaner and more reliable analysis: By keeping only YEARLY salary postings, I ensure that all salary values reflect the same pay structure. This allows for fair comparison across skills, experience levels, locations, and work types without distortion.
  4. Large enough sample size: After filtering to YEARLY pay_period, the dataset still retains a sufficiently large number of job postings to perform meaningful statistical analysis and visualisation.

Overall, choosing YEARLY salaries simplifies the analysis and improves accuracy while avoiding unnecessary assumptions.

Creating a Unified Salary Column¶

The dataset contains three salary fields: med_salary, min_salary, and max_salary. However, these values are not populated consistently across postings. Some jobs provide only a median salary, while others list only a minimum–maximum range. If I were to use only med_salary, I would lose more than 90% of the yearly postings, resulting in a very small dataset after filtering for tech roles.

To retain as much valid data as possible, I created a single unified salary estimate column called salary_est using the following logic:

  1. Use med_salary when it is available: the median salary is already standardized and is the most reliable central estimate
  2. If med_salary is missing but both min_salary and max_salary are available, I estimate the salary by taking the midpoint of the range:
    salary_est = (min_salary + max_salary)/2
  3. Remove rows with no usable salary information: rows missing all three fields
  4. Handle unrealistic outliers: Remove postings where max_salary is more than 4× min_salary, as these represent unrealistic or noisy ranges & apply the IQR rule to salary_est to remove extremely low or high outliers.

This approach allows me to use a much larger portion of the dataset while still ensuring that the salary values are consistent, comparable, and not distorted by extreme outliers. The final salary_est column will be used for all salary-related analysis in this project.

What is the IQR Rule?¶

The Interquartile Range (IQR) rule is a method used to detect and remove outliers. It uses the middle 50% of the data (between Q1 and Q3) to define reasonable values. Any value outside the range:
Q1-(1.5IQR) to Q3+(1.5IQR)
is treated as an outlier.
This helps remove unrealistic salary values without affecting the main distribution.

In [124]:
# create unified salary_est column 
df['salary_est'] = df['med_salary']  # use median when available

# when med_salary is missing but min and max exist, use midpoint
mask = df['salary_est'].isna() & df['min_salary'].notna() & df['max_salary'].notna()
df.loc[mask, 'salary_est'] = (df.loc[mask, 'min_salary'] + df.loc[mask, 'max_salary']) / 2

# drop rows with no salary info at all
df = df.dropna(subset=['salary_est'])

# remove rows with unrealistic min–max ranges (max > 4 times min) 
range_mask = df['max_salary'].notna() & df['min_salary'].notna()
df = df[~((df['max_salary'] > df['min_salary'] * 4) & range_mask)]

# remove global salary outliers using IQR method 
q1 = df['salary_est'].quantile(0.25)
q3 = df['salary_est'].quantile(0.75)
iqr = q3 - q1

lower_bound = q1 - 1.5 * iqr
upper_bound = q3 + 1.5 * iqr

df = df[(df['salary_est'] >= lower_bound) & (df['salary_est'] <= upper_bound)]

This ensures that:

  • the column correctly reflects whether remote work is offered
  • all values are numeric
  • field can be used directly for grouping and salary comparison.

Final Conclusion¶

My analysis shows that salaries in the tech industry vary meaningfully across several key job factors.

Experience level has the strongest influence: median salaries rise clearly from Internship and Entry-level roles to Mid-Senior, Director, and Executive positions. The distribution charts confirm that higher experience levels consistently command higher pay, even though their salary ranges do not necessarily widen.

In contrast, remote eligibility does not appear to significantly affect median salary. Although remote roles make up only about 29% of all postings, their median pay is almost identical to non-remote jobs, suggesting that allowing remote work does not reduce or increase salary levels in this dataset.

Location also plays an important role. Major tech hubs such as Seattle, San Francisco, and San Jose offer the highest median salaries, while cities like Charlotte and San Diego fall on the lower end. This geographic variation highlights that tech salaries partially reflect regional market demand and cost-of-living differences.

Overall, my research finds that experience level & location are strong influencers of tech salaries, while remote eligibility has minimal effect.
